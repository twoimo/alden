The scan connection now requests a 256 MiB mapping limit separately for its main and attached read-only derived databases, before scan cursors start. An admitted limit of at least 256 MiB allows an 8 MiB private cache; missing, zero or insufficient admission retains the prior 64/32 MiB schema-specific cache. Operational errors still fail the action. These are request-local settings, without persistent PRAGMAs, schema changes, `immutable=1`, forced checkpoints or a larger product deadline. Mapping admission is a limit, not proof of mapped coverage or resident memory. [SQLite's official mmap description](https://www.sqlite.org/mmap.html) explains the shared-page mechanism, limits and I/O-fault tradeoff.

Four separate pinned-runtime diagnostic processes in ABBA order observed baseline 13.667/5.661 seconds and 256 MiB mapping with the old caches 3.838/5.441 seconds. Later baseline/old-cache mapping/small-cache mapping observations took 17.983/15.634/7.380 seconds. All complete reports had the same hash after removing only `elapsed_s`. Warmth, memory pressure and host contention were uncontrolled, so these are observations rather than a causal speedup estimate or a deadline guarantee.

The later owned-process `vmmap` observations reported peak physical footprints of 298.9M/260.6M/162.5M (the vmmap labels), while peak RSS was 319,373,312/579,092,480/488,816,640 bytes respectively. RSS and physical footprint measure different things; this is not an RSS reduction claim. A 1 GiB main mapping experiment produced the same report in 7.832 seconds, with higher RSS 684,834,816 bytes, and was not selected. Initial source execution with the selected settings took 10.148 seconds under the diagnostic horizon, then the actual 10-second actions completed in 4.182 seconds without source comparison and 5.687 seconds with comparison. After the retrieval lifecycle guard, the actual actions completed again in 9.051/3.971 seconds with identical responses apart from observation timestamps. Reliable p95 and cold/pressured completion remain unmeasured.

The ordinary quality action now checks the retrieval file's device/inode/mode as well as the existing collection identity and permission checks before accepting a report. Retrieval replacement, removal or appearance during inspection rejects the result. Ordinary WAL commits retain the established per-database read snapshots; separate databases are not claimed to share one global snapshot. Real mapped I/O faults can terminate a subprocess. The native process supervisor already rejects non-success exit status before accepting output. A disposable mapped-file truncation regression verifies that even success-shaped stdout cannot turn such a worker fault into a successful action. It does not establish arbitrary live SQLite truncation recovery.

## CPU candidate and rejected query changes

Private-snapshot membership-rowid, relation-rowid and narrow ordered-relation query experiments retained complete observed reports or row sequences, but did not establish a repeatable warm advantage. They were not adopted. The production query, row order, malformed-record names and finding sample order remain unchanged.

The CPU candidate reuses a strict JSON decoder per calling thread, preserves byte encoding detection, and retains duplicate-key/nonfinite/overflow rejection. It reuses at most 64 exact validated vector-profile digests within each serial audit, while inspecting every vector's bytes and dimensions. It reuses a content classification only when the original body and effective body are exactly equal and both calls have the same stored-body provenance. Byte lengths are accumulated locally before the existing per-row counter update and budget check. No parsed source object, vector validation result or report is cached across records or requests.

The first private six-process comparison observed original wall times 8.057/3.812/3.439 seconds and candidate 3.627/3.524/3.240 seconds. All six complete reports, including cap-two samples, had the same hash excluding only elapsed time. The first original was colder; host contention was uncontrolled. These observations are not a causal percentage, p95, whole-app, quota or deadline-reliability claim. The final source uses a per-thread decoder after the supplied-code Web Astra review identified shared-scanner concurrency uncertainty; its exact-source comparisons and product actions are recorded separately.

Tests cover encoding/type errors and recovery, distinct decoders in overlapping threads, verified provenance despite equal bodies, a retained body differing from a stored URL reference, and 132 vectors across 66 profiles with different dimensions. The original fixture's eight placeholders for seven vector columns was a test-harness error, corrected without changing production behavior. The full 18-item goal, physical UI/voice, independent semantic gold and signed production release remain separate gates.

The final source passed 158 related quality, source-text, relation-binding, annotation-candidate and entity-resolution tests. Complete fixed-snapshot reports matched the installed 0.3.115 for sample caps 0, 2 and 10 after removing only elapsed time, including counts, findings, bytes, scope and sample order. Actual derived-store actions with the unchanged 10-second limit completed in 6.949 seconds ordinarily and 3.501 seconds with source comparisons. These are two action observations, not cold/p95 guarantees; candidate and installed native gates must still pass for delivery.
