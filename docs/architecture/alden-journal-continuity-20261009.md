# Alden journal continuity and scoped counts

0.3.48 gives a collection store a persistent journal identity before its first event. Previously the first commit changed the empty journal's identity, so a visible graph discarded that first event as a reset. Identity and first-event anchor now commit with the private store. A pruned first event, replacement or cursor rewind still requires a fresh scoped snapshot. Historical events never become fresh visual activity. Legacy read-only stores retain their existing identity until the ordinary writer initializes the extension.

History pages carry the same scoped stream identity and a high-water cursor. A replaced or rewound journal returns a fresh recent page and exact aggregate; the frontend clears old rows, expanded evidence and stale counts. Empty histories begin forward recovery at cursor zero. Hidden views stop requests; restored views retain one consumer and page through unread stages. Target sequence gaps remain legitimate, and stage filters do not alter permission boundaries.

The summary counts stage receipts separately from stored additions, revisions and unchanged records. Its scope matches project, target, platform, stage, search and local-date filters. A save receipt is not factual validation, a text-index receipt is not dense-index proof, and a read is not a knowledge change. Details retain the actual collector origin and run/version/source identities. Project labels outside the requested project set are excluded.

Default and stage-only summaries read exact per-target counters. Insert, delete and update triggers maintain them in the same transaction as the journal, including older writers, duplicate rejection and rollback. Time/search filters count their exact matching receipts without extrapolation. Counters and the target/sequence index are optional schema-3 accelerators; original records and existing schema readers stay compatible. A one-time, private online-backup recovery copy precedes initialization on an existing store. Read-only lookup does not migrate or create storage.

The first full-size trial exposed a planner regression: the new target index made overview pages join and sort the entire journal. Retained failure measurements document this. Final overview pages use the integer-primary-key keyset order, and checkpoint endpoints use bounded per-target lookups. Full aggregation is not repeated by 2.5-second forward polling; the visible consumer increments matching counts from newly committed, deduplicated pages.

An online-backup clone of the real store contains 266,252 permitted stage receipts at cursor 266,255. All ten source/projection/history table hashes and row counts remained identical through extension initialization; integrity passed and all 51 counter groups matched an independent full-journal query. Original source files were not copied or changed. Five alternating warm history calls took median 1.19ms for the prior row-only API and 1.64ms for the new rows-plus-summary API. A separate five-pair checkpoint SQL comparison on the same clone/index returned identical cursor ranges and medians 52.09ms versus 13.03ms. These are local SQL operations, not UI p95, FPS, GPU, battery or quota measurements.

Regression checks cover first commit after an empty baseline/reopen, replacement and rewind, scope/date/stage filters, duplicate replay, rollback, counter edits/deletion, recovery backup permissions and one-time initialization. Renderer tests require a first saved receipt's exact version to be visible before it can pulse. Source tests, native captures, installation/signature, actual live migration and CI are separate delivery gates; the outputs/history-journal-20261009 receipts record them. Broader multi-host acquisition, shared OSK wiring, physical gestures/voice, independent real-source gold, DPO, signed release and production remain in the full goal.
