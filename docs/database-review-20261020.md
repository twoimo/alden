## Actual storage and baseline

The collection store uses transactional source/version/membership/event records, retained content-addressed blobs, permission-scoped projections and FTS5. Retrieval is a derived, rebuildable text/vector projection, not graph authority. Durable scheduler and live-detection state have separate ownership; that separation alone does not require different database engines.

## Reproduced query improvement

The indexer loaded metadata for every retained vector, including historical versions and unrelated project scope. Candidate code reuses the already constructed `source_text_scope`, probes `(document_id, version)` through the existing vector primary key and leaves source verification, profile stamps, vector reuse, permissions, cancellation and publication semantics intact. No persistent schema/index migration is involved.

Read-only production metadata experiment, six alternating samples per method:

| Admitted scope | Matching vectors | Full scan median ms | Scoped query median ms |
| --- | ---: | ---: | ---: |
| 10 current versions | 10 | 69.07 | 1.54 |
| 1,000 current versions | 983 | 68.65 | 3.31 |
| 26,623 current versions | 26,163 | 64.46 | 50.00 |

All admitted stamps matched exactly on every comparison. Query plan: scope scan plus indexed vector lookup. Temporary scope construction was separately measured (0.02 / 1.08 / 37.30 ms); the product already constructs that table for source projection before either SELECT, so this change adds no second scope build. Measurements include no embedding inference, source hashing, text extraction, writes, vector similarity, GUI rendering or cold-start claim. No whole-app speed, RAM, battery or quota gain is inferred.

Local evidence: `outputs/realtime-collection-20261020/database-baseline.json` and `vector-metadata-comparison.json`, generated by the two scripts in `docs/audits/`. Reports retain script hashes; private keys never leave process memory.

Installed 0.3.192 testing exposed an acquisition/queue handoff defect: refreshing an input could leave its pre-acquisition change hint queued after successful indexing. The 0.3.193 repair consumes only the published signature or the exact hint admitted for that attempt; a newer queued hint remains pending. A real receiver/collector regression now verifies that a refreshed native source does not trigger another poll before the 60-second floor. The initial installed observation is retained separately and is not claimed as a passing final runtime test.

## Alternative engines and decision conditions

| Candidate | Role worth testing | What must be proven for Alden |
| --- | --- | --- |
| SQLite | Local transactional source of truth, FTS and small control state | Bounded writer hold/busy retries; WAL growth/checkpoint age; permissions and crash recovery at real collection/read concurrency |
| PostgreSQL + pgvector | Shared service when independent hosts need concurrent transactional writes; combined relational/vector querying | Same provenance/time/permission answers, offline behavior, service memory/maintenance/backup cost and migration/rollback correctness; exact and approximate retrieval must be evaluated separately |
| Qdrant | Optional derived vector-search projection when measured candidate search dominates | Recall at fixed latency/RSS, filters before/after ANN, version deletion/rebuild, permission isolation and service costs; it would not replace source/version transactions |
| Neo4j | Optional graph-query projection for demonstrated variable-depth traversal workloads | Measured multi-hop workload advantage, permission/time semantics, index/refresh costs and recoverable synchronization; graph visualization itself does not require a graph DB |
| DuckDB | Offline analytical evaluation of events/graph snapshots | Batch-query advantage and isolated resource limits; its concurrency model is not evidence for replacing the interactive multi-process writer |

Primary sources reviewed on 2026-10-20: [SQLite use cases](https://sqlite.org/whentouse.html), [SQLite WAL](https://sqlite.org/wal.html), [PostgreSQL MVCC](https://www.postgresql.org/docs/current/mvcc.html), [pgvector](https://github.com/pgvector/pgvector), [Qdrant storage](https://qdrant.tech/documentation/concepts/storage/), [Neo4j indexes](https://neo4j.com/docs/cypher-manual/current/query-tuning/indexes/), [DuckDB concurrency](https://duckdb.org/docs/stable/connect/concurrency). These establish engine capabilities and constraints, not an Alden benchmark winner. The roles and decision conditions above are engineering hypotheses.

## Work sequence and measurable gates

1. Preserve current identity/version/history semantics and every configured collection target, interval, permission and emergency state. Inventory the true consumers and query plans before changing schemas. Capture existing known-good signature/config receipts.
2. Deliver the bounded scoped-query repair and live scheduler independently of any database replacement. Verify unchanged/revised/missing sources, interrupted indexing, queue coalescing, duplicate requests, concurrent controls, source changes during indexing, denied targets, paused/voice/emergency states and encoder-profile changes. Background/headless QA only; no test knowledge or sends in the user's store.
3. Measure the full actual path: input detection → acquired source → retained version → FTS/vector ready → graph journal/INGEST/TAIL-F. Record p50/p95/p99, failures, retry count, writer lock duration, WAL growth, RSS/CPU and source-to-visible lag. Compare identical source/event workloads; file detection has a 5-second poll plus settle/cycle/processing delay, authorized video polling at least 60 seconds. Neither promises instant completion or channel-wide discovery.
4. Run repeatable shadow experiments on permission-reviewed data with the same query corpus and independently held relevance/identity/temporal gold. Keep actual-scale and 10× synthetic workloads separate. Include latest-version search, literal Korean search, metadata filtering, multi-hop graph navigation, event keyset pagination, one-record changes, large snapshots and simultaneous readers/writers. Capture engine/version/config/query plans and cold/warm conditions. A SELECT microbenchmark cannot select an engine.
5. Establish latency/resource acceptance budgets from the baseline and user workflow, then subject them and the workload coverage to external review before choosing a winner. Require zero changed authority/permission/time answers, no lost or duplicated committed events, deterministic queue recovery and source-to-index parity. Report ANN recall against exact ground truth at each resource/latency point; do not compare different recall as equal work.
6. If a new engine clears those gates, first build a disposable, rebuildable shadow projection. Preserve SQLite as authority until snapshot plus ordered event catch-up are reconciled at a common checkpoint. Avoid uncoordinated dual writes. Rehearse failure/recovery, digest/count/version/permission comparisons, backup restore and rollback before any product cutover. No migration, new always-on service or paid capacity was authorized merely by this document.
7. Complete fixed-signature build/install/readback and real runtime validation for the final chosen implementation. Distinguish local tests, background rendering, installed CLI, actual service execution and external release. Keep the full 18-item goal active.
